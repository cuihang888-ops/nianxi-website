# 安和里 · 德宏世界开发框架

日期：2026-11-13。产品方向由用户确认；中心寺院指定为瑞丽总佛寺。本文区分当前原型和后续建设方案，不代表完整德宏地图、云端资产或充值已经上线。

## 世界目标

把安和里发展为一片以德宏为灵感的原始山林世界。来客可以选择喜欢的地区安家，照顾动物、种植、沿山路旅行，或到瑞丽总佛寺静坐、祈愿和相聚。交通只有步行与骑马，不加入汽车、现代公路或即时传送作为常规出行。

“原始”指本游戏的架空世界设定，不对现实德宏或当地居民的生活方式作描述。第一版地图采用游戏化的相对位置、道路和景观，不作为行政区划图、测绘地图或历史复原。区域路线的耗时是游戏参数，不是现实旅行时间。

产品延续 `PRODUCT_INTENT.md`：动物不因缺席死亡，基础祈愿和相聚不收费，不通过土地抢购、排名、断签损失或强制日课制造压力。寺院活动不与付费好运、功德等级或收益倍率绑定。

## 地图与安家

世界分为芒市、瑞丽、陇川、盈江、梁河五个区域。以下为美术和玩法提案，聚落名与土地均为虚构，不对应现实土地权属。

| 区域 | 设计主题 | 安家体验 | 公共地点 |
| --- | --- | --- | --- |
| 芒市 | 缓坡、林间水田、晨雾 | 林缘小院、缓坡牧场 | 歇脚亭、种子集市 |
| 瑞丽 | 江岸、竹林、开阔河谷 | 江岸家园、竹影草场 | 瑞丽总佛寺、公共集市 |
| 陇川 | 山谷、草坡、山间溪流 | 谷地牧场、溪畔小院 | 马厩、山路驿站 |
| 盈江 | 江流、湿润林地、宽阔草甸 | 河谷农庄、林间草甸 | 观鸟地、采集营地 |
| 梁河 | 溪谷、丘陵、静谧林间 | 溪谷家园、山麓小院 | 茶亭、山林入口 |

每位玩家拥有自己的家园实例。选择某个地区及聚落样式，不会占走其他玩家的唯一位置；任何人都能在喜欢的地区获得基本归处。“买地”购买的是游戏内的家园扩展权，不是现实不动产，也不制造可炒卖的稀缺地契。

首次选址免费；原型迁居免费，已有动物、菜畦、昵称、物品和余额随家园保留。后续如增加房屋布局，需要存储可复用的家园布局坐标，在迁居时重建地形底座，不重新发放资产。迁居不得成为反复领取新手奖励的入口。

瑞丽总佛寺是公共社交目的地，承接当前静坐、木鱼、念珠、心灯、喝茶和同意式邀茶。先使用现有庭院作为功能原型；建筑外形与院落布局单独建立参考资料，再做美术调整，不把当前模型宣称为准确复刻或寺院官方项目。原万年历与自动罗盘独立保留。

## 一次游玩的主线

进入世界后可以直接在庭院停留，也可以打开地图选一个地区安家。家园内买地、养动物和种植形成简单循环；产物可出售给系统集市换取安币。地图显示家园、所在地区、目的地和道路，外出沿路步行，拥有马匹后可以骑乘。返回寺院不要求先完成农场任务。

狩猎集中在明确划出的山林区域，沿用现有无血腥的轻量玩法。动物陪伴、采集、种植同样能提供资源，不让狩猎成为维持家园的必选项。家养动物的照料与野外探索使用不同交互，避免误操作。

## 交通与场景加载

宏观地图保存区域节点、公共地点、聚落入口和道路图；局部场景处理脚下寻路、碰撞和角色动画。跨区先在道路图计算路线，再沿局部出口进入下一段场景。道路中的岔口、溪桥和歇脚点让旅途本身可玩。

步行与骑马共用道路可达性规则。骑马是移动方式与陪伴系统，不能穿过围栏、建筑或水体；寺院内按地点规则下马。马匹可以取名和被照料，不设置因离线饥饿死亡或付费恢复体力。原型领养马匹和路线速度参数均属于可调整的游戏规则。

完整多人版本由服务端保存 `travelId`、当前位置、道路段、交通方式和最后确认时间。客户端不能提交“已经到达”来跳过验证；重连回到最后确认的安全地点，场景加载失败时留在原地点，不扣款、不丢资产。

渲染按区域切片加载，建议起始切片边长为 64 个游戏单位，按实测调整。只保留当前及相邻切片的高细节对象，远景使用简化山体、树群和低频动画。静态模型按材质合批，花草与动物继续使用实例化绘制；离开切片明确释放几何、纹理和监听器。

联机也按当前地点及邻近范围订阅。公共寺院、聚落广场和好友家园分别拥有实例编号，人数是真实连接数。先沿用每个公共实例最多 24 人的现有容量，再以压力测试决定扩容；不将全服每个人、每只动物同时广播给所有客户端。同队或受邀好友优先进入相同实例，满员时明确提示。

## 经济设计

界面统一称“安币”。现有 `coins` 字段和数值保持不变，原“叶币”只是显示名迁移，不给老玩家重复赠送余额。安币用于游戏内土地扩展、动物、种子、马匹和后续家园装饰。基础土地与伙伴应能通过普通游玩获得，付费不是进入世界或长期照料动物的条件。

首版只有游玩获得的安币；不设真实付款入口、不接商城订单、不从浏览器写入充值余额。后续支持充值时，界面仍可显示一种安币，服务端必须分开记录获得来源：

| 来源 | 入账依据 | 使用与限制 |
| --- | --- | --- |
| 游玩获得 | 服务端验证的收获、出售、固定补给 | 用于普通游戏消费，不兑换现金 |
| 充值获得 | 已核验的支付订单、版本化兑换比例 | 有订单关联和退款追踪，不由客户端发放 |
| 活动赠送 | 服务端活动规则与唯一发放记录 | 单独记录活动及是否随退款撤回 |

不要增加“积分换安币再换游戏币”的多级兑换。未来是否增加外观专用点数，要基于实际商品需求单独决定。首轮经济没有玩家间转账、现金提现、外部交易或地价涨跌；系统集市使用明确固定价格，避免为开放玩家市场过早增加欺诈、通胀和资产追踪复杂度。

记录资源发行与消耗：新手赠送、日常补给、产物出售是主要发行项；土地扩展、动物、种子和装饰是主要消耗项。上线后观察新玩家获得第一块地与第一只动物所需时间、余额分布、每日净发行、长期未消费余额和免费玩家体验。不要以让玩家余额归零或强迫充值作为调价目标。

## 持久化与服务边界

当前 `service/server.mjs` 只在内存中同步匿名来客、房间、位置和临时互动，重启会清空。个人农场仍保存在浏览器 `anheli-farm-v1`；它可以被本机用户修改，不能作为付费资产凭证。持久多人版本需要安和里自己的账号标识、数据库与资产服务，和商城数据库分开。

建议服务模型如下，字段为设计契约而非已存在的数据表：

| 实体 | 核心字段 | 不变量 |
| --- | --- | --- |
| `Player` | `playerId, accountId, createdAt, schemaVersion` | 账号由服务端认证，不接受客户端自报身份 |
| `Homestead` | `homeId, ownerId, regionId, settlementId, layoutVersion, revision` | 迁居只改变位置元数据，资产归属不变 |
| `Asset` | `assetId, ownerId, homeId, type, sourceTransactionId, state, revision` | 每次领养、购买、收获都有唯一来源 |
| `Wallet` | `walletId, playerId, currency, balance, revision` | 币值为有界整数，已提交余额不能为负 |
| `LedgerTransaction` | `transactionId, playerId, reason, idempotencyKey, orderId, createdAt` | 玩家与幂等键唯一，记录不可覆盖 |
| `LedgerEntry` | `transactionId, accountId, sourceBucket, delta, currency` | 同一交易、同一币种的分录合计为零 |
| `PaymentOrder` | `orderId, playerId, productId, priceVersion, amountMinor, fiatCurrency, grantAmount, providerTradeId, state` | 支付金额、发币量由服务端目录生成 |
| `Journey` | `travelId, playerId, regionId, routeId, segment, position, mode, revision` | 位置和骑乘资格由服务端验证 |

系统发行与回收也记账，分别使用发行账户和回收账户。法币金额与安币分属不同币种的账本，不混算；两套交易通过 `orderId` 关联。法币使用最小货币单位整数，安币使用整数，避免浮点数金额计算。所有发放、扣币与资产创建在一个数据库事务中提交，失败整体回滚。

拟议模块边界：

| 位置 | 职责 |
| --- | --- |
| `src/world-state.js` | 原型区域目录、聚落选址、交通方式和道路计算 |
| `src/farm-state.js` | 现有纯养成规则与兼容迁移，不接真实收款 |
| `src/scene.js`、`src/farm-scene.js` | 角色、家园、动物、当前场景；后续拆出切片加载器 |
| `service/server.mjs` | 现有临时多人协议；升级时保持兼容或明确协议版本 |
| 后续 `service/world/` | 服务端位置、道路和实例分配 |
| 后续 `service/assets/` | 家园、动物、物品与原子购买指令 |
| 后续 `service/economy/` | 钱包、分录、价格目录和对账 |
| 后续 `service/payments/` | 支付适配器、订单、回调和退款，不处理游戏碰撞或画面 |

将来如需关联商城账号，只通过明确授权的身份交换接口建立映射，不读取商城密码或直接复用商城数据库表。当前工作不改商城支付、订单、会员、商品与 ERP。

## 充值与交易契约

以下为后续服务接口设计，本轮没有这些可用端点：

| 命令 | 客户端提供 | 服务端负责 |
| --- | --- | --- |
| `POST /world/home` | `regionId, settlementId, expectedRevision, idempotencyKey` | 校验目录与玩家，原子迁居，返回新版本 |
| `POST /assets/purchase` | `sku, quantity, expectedRevision, idempotencyKey` | 查价、资格、容量、扣币与发资产 |
| `POST /payments/orders` | `productId, idempotencyKey` | 固定币种、价格和兑换版本，建立待支付订单 |
| `POST /payments/webhook` | 支付平台原始通知 | 验签、商户/订单/币种/金额匹配、去重与状态核验 |
| `GET /payments/orders/:id` | 订单 ID | 校验归属，返回权威状态；前端只展示 |

支付完成以验签回调及必要的平台查单结果为准，不采信前端跳转页、客户端传来的金额或“支付成功”布尔值。`providerTradeId` 和回调事件 ID 建立唯一约束，重复、乱序、超时重试不得重复发币。用户刷新、网络中断和服务重启后仍能查到同一订单。

订单状态区分待支付、平台已支付、发币完成、关闭、退款处理中、已退款与人工核对。支付确认和发币用持久事件可靠衔接：平台已收款但发币失败时进入补偿队列，重试只完成同一笔发放。定时对账核对平台订单、内部订单与账本，不以日志文本代替账本。

消费分录明确从哪个来源余额扣除。建议先扣赠送及游玩所得，再扣充值所得，并保留对应资产的资金来源比例，避免退款时无法区分充值资产。退款使用逆向分录，保留原始交易；已消费订单进入有记录的人工处理流程，不直接修改旧记录、不制造负数余额，也不误删与该订单无关的动物。

真实收款开始前，需要确定商户及支付渠道、商品目录、兑换比例、退款说明、账号恢复方式、适用玩家范围和客服处理流程，并完成订单、通知、退款与对账的沙箱验收。这里是产品和工程上线条件，不把本地游戏测试视作支付验收。

## 三阶段交付

| 阶段 | 交付范围 | 完成依据 |
| --- | --- | --- |
| 一：世界原型 | 五区地图入口、聚落选址、家园元数据、安币名称、马匹资格、步行/骑马路线参数；延续现有牧场与寺院玩法 | 老存档无损，选址及换区不增减资产，非法区域和重复购买被拒绝，桌面与手机可用 |
| 二：持久多人世界 | 独立账号、云端家园和资产、可游玩的区域场景、道路切片、马匹模型和骑乘动画、真实访友及公共实例 | 断线重连可恢复，并发消费不超扣，服务重启不丢资产，真实多人互访、道路和低端设备性能验收 |
| 三：真实充值 | 商户渠道、服务器钱包、支付订单、验签发币、退款和对账；可用开关控制开放 | 沙箱重复/乱序回调、失败补偿、退款与查单通过，小范围上线回归完成 |

第一阶段的地图选址不等于五地完整地形已经建好；路线规划不等于真实跨区旅行已经联机；选择骑马不等于马匹动作、同步和碰撞已经完成。验收与界面状态要反映各自实际进度，不用假在线玩家或假交易营造完整度。

## 存档迁移和验收重点

现有 `version: 1` 农场存档增加可选世界字段，缺失时补默认值；余额、地块、动物 ID、名字、照料状态、菜畦和物品保持原值。每次改版先用旧存档做迁移回归，保存失败继续沿用已有明确提示，不能显示“已保存”。

未来迁到云端时，本机旧存档只作为玩家进度导入申请，不把可篡改余额转换成付费余额。服务端用一次性迁移记录、范围校验和明确的导入政策接续游戏进度；保留原存档副本，冲突时给出可理解的结果，不静默覆盖。

重点测试安家与迁居、跨窗口更新、余额上限、重复购买、骑乘资格、道路不可达、服务端消费并发、好友家园权限、切片释放、弱网重连和减少动态模式。地图与马匹相关改动要检查桌面及手机真实画布、实际移动、点击命中和遮挡。原万年历 15 个源文件与构建文件持续做哈希核验。

所有源码、截图、报告、缓存和构建留在 D: 项目目录。这里只制定与实现安和里范围内的框架，不自动部署线上商城；发布前单独核对本次变更、服务兼容与实际验证结果。

## Codex 与 Muse 协作

用户明确分工：Codex 负责大框架、规则与实现闭环，Muse 负责细节和画面。双方先约定数据、坐标和资源接口，再各自在负责的模块内迭代，最后由 Codex 合并并验证完整体验。

| 负责人 | 负责范围 | 交付边界 |
| --- | --- | --- |
| Codex | 区域与聚落目录 ID、存档及迁移、道路图、安币规则、服务端资产、联机契约、平台适配接口和集成测试 | 保证选址、旅行、消费、存档和多人之间能形成完整流程；不把画面完成度当作规则已验证 |
| Muse | 后续 `world-art/` 与 `assets/` 内分区地形、瑞丽总佛寺文化参考、动物与马匹动作、材质和细节层级 | 依据已约定的实体 ID、碰撞范围与动画状态提供画面，不直接修改经济或存档数据 |

拟议美术资源描述文件使用 `assetId, regionId, uri, license, lods, bounds, collisionProxy, animationStates, anchorPoints`。资源 ID 保持稳定；模型原点、缩放单位、朝向和道路出口锚点在首次交付前确认。动画由语义状态驱动，例如站立、行走、进食、回应和骑乘，不反过来让动画回调发币、迁居或变更资产归属。

双方每轮从最新已合并基线创建自己的分支，交付中标明基线提交与修改文件。Muse 不覆盖 `src/world-state.js`、`src/farm-state.js` 及未来服务端规则；需要调整容量、速度或碰撞契约时先提出参数改动，再由规则负责人同步测试。Codex 对共享场景文件采用逐项合并，保留双方既有修改，不整体覆盖旧 ZIP。

美术交付包含桌面与手机截图、可运行场景、素材来源与许可证、真实测量的面数、绘制次数、纹理占用和帧时。每个区域给出可调整的 LOD 层级和碰撞代理；预算以同一视角、同一动物数量与目标设备实测确定。没有测量时明确写“待测”，不虚构性能数据。微信目标确定后增加对应真机检查。

此文档是下一轮交接依据，不表示已向 Muse 发送消息、上传文件或建立自动协作。实际交付仍通过用户指定的仓库分支或文件包完成。

## 独立微信产品目标

建议安和里作为独立产品规划，并优先评估微信小游戏作为微信端目标；网页版保留为快速开发、演示和回归测试入口。现有核心体验是持续运行的三维世界与养成游戏，因此先围绕游戏运行形态验证可行性，不把整个年禧商城一并迁入。产品定位、主体、接入方式及审核结果均需要在正式接入前核实，本框架不承诺已获得平台支持或审核通过。

当前没有项目 AppID、已配置微信渠道或真实充值入口。第一步是完成最小运行验证：能在目标运行环境显示场景、移动、选中动物、恢复一份测试存档，并测量加载时间、内存与帧时；通过后再迁移完整地图。不能把 React 网页打包后直接视作已完成微信小程序或小游戏。

纯规则层保持平台无关，继续共享区域目录、道路计算、养成规则、数值校验与迁移测试。`React DOM` 界面、浏览器事件、资源加载、Canvas 创建、音频、文件导出和存储访问需要平台适配；Three.js 的使用方式也要通过目标环境中的实际运行验证，再决定保留或替换哪些渲染部分。网页中的万年历与自动罗盘保持原文件，微信端如何承载另行验证，不为迁移而直接改写原版资源。

拟议适配层如下：

| 接口 | 网页原型 | 微信目标与服务端责任 |
| --- | --- | --- |
| `PlatformSession` | 当前匿名访客会话 | 平台登录结果由后端验证并关联安和里账号，客户端不自报账号归属 |
| `SaveRepository` | 浏览器本机存档 | 本机缓存加服务端权威存档，提供版本、冲突和恢复结果 |
| `WorldRenderer` | 现有浏览器 Three.js 场景 | 隔离 Canvas、生命周期、输入、资源解码与音频差异 |
| `InputAdapter` | 鼠标、触摸、界面按钮 | 统一移动、选中、交互等语义指令，不让平台事件进入规则层 |
| `PaymentAdapter` | 未开放 | 依据确定的渠道实现订单发起与结果展示，服务端核验后入账 |

账号、云存档、资产和账本使用安和里自己的稳定 ID，平台身份只是登录来源，避免今后网页与微信出现两份无法合并的家园。旧本机存档依照前文的迁移政策导入，不把本地余额提升为付费资产。账号恢复、跨设备冲突和同账号多端互斥策略要先测试，再开放充值。

微信端接入以平台当时的官方文档、目标终端和实际账号条件为准；支付能力通过可用性配置控制，不硬编码尚未确认的渠道规则或金额比例。没有完成真实渠道与账本验收时，界面保持充值未开放，不展示可成功付款的模拟流程。

## 官方接入资料核对

2026-11-13 已读取以下官方资料。它们是平台接入参考，原型本身尚未通过微信运行或发布验收。

- 微信小游戏开发指南：`https://developers.weixin.qq.com/minigame/dev/guide/`。将小游戏作为独立客户端验证，保留网页开发入口。
- 虚拟支付进件：`https://developers.weixin.qq.com/minigame/dev/guide/open-ability/virtual-payment/virtual-payment2.html`。页面列出已认证主体、实名认证系统以及版号/软著相关材料等开通条件；实际资格以申请账号控制台及平台核验为准。
- 虚拟支付技术手册：`https://developers.weixin.qq.com/minigame/dev/guide/open-ability/virtual-payment/guide.html`。游戏币与道具直购分开设计；微信游戏币托管模式的权威余额及扣币由平台接口管理。未来 PaymentAdapter 应对接选定模式，内部账本用于来源、订单、对账和资产关联，不能在平台余额之外另行重复发放。
- Web-view 组件：`https://developers.weixin.qq.com/miniprogram/dev/component/web-view.html`。网页承载与原生游戏客户端是不同接入方案，不能将当前网页可访问当作微信客户端完成。
- 微信团队 Three.js 小程序适配示例：`https://github.com/wechat-miniprogram/threejs-miniprogram`。其 README 标注基于 Three.js 0.108.0，当前项目使用 0.187.0；不直接用旧适配包替换现有引擎，先做隔离的最小运行验证。
