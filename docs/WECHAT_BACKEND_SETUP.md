# WeChat session service setup

Status: implemented and tested with an injected WeChat response. No real AppID or AppSecret has been configured, no real WeChat login has been completed, and nothing has been deployed. This service is separate from the current presence server, farm rules, payment, marketplace, and calendar.

## Official integration references

The official migrated `code2Session` documentation was read in the browser on 2026-11-13:

`https://developers.weixin.qq.com/minigame/dev/api-backend/login/api_code2session.html`

It specifies a server-side GET to `https://api.weixin.qq.com/sns/jscode2session` with `appid`, `secret`, `js_code`, and `grant_type=authorization_code`. The response supplies `openid` and `session_key`; `unionid` may be absent. A successful response can contain `errcode: 0`, which this implementation accepts. Documented errors include `40029` (invalid code), `40226` (risk interception), and `45011` (too frequent). The service returns stable local errors without forwarding WeChat response details; `40226` becomes HTTP 403 `WECHAT_RISK_REJECTED`, and `45011` becomes HTTP 503 `WECHAT_UNAVAILABLE`. This document verification is not a completed live integration: test a real exchange in the WeChat developer tools with this game's actual AppID before declaring login connected.

## Configuration

The service is disabled unless `ANHELI_WECHAT_AUTH_ENABLED=1` and all required server variables pass validation:

| Variable | Purpose |
| --- | --- |
| `ANHELI_WECHAT_APP_ID` | One fixed registered game AppID. Client-supplied AppIDs are rejected. |
| `ANHELI_WECHAT_APP_SECRET` | The AppSecret for that AppID, kept only in the service environment. |
| `ANHELI_WECHAT_PLAYER_ID_SECRET` | Stable high-entropy identity HMAC key; use at least 32 random bytes encoded as base64url. Never rotate casually. |
| `ANHELI_WECHAT_AUTH_HOST` | Optional bind address, defaults to `127.0.0.1`. |
| `ANHELI_WECHAT_AUTH_PORT` | Optional port, defaults to `4108`. |

The identity key must have at least 32 bytes of string material and at least eight different characters; these syntactic checks cannot guarantee entropy. No production keys are generated by this task. Do not place secrets in the client, repository, public environment variables, logs, screenshots, or Muse handoff. The HMAC maps the pair `(AppID, OpenID)` to a stable pseudonymous player ID. Changing this key changes every identity and requires an explicit migration.

After a server operator supplies these variables through the deployment environment, start the isolated process with `node service/wechat-auth.mjs`. With the default environment it starts listening but returns `503 WECHAT_AUTH_UNCONFIGURED` for auth routes. Importers can call `createWechatAuthServer(options)` and use the normal Node HTTP server `listen()` / `close()` methods.

## Muse client contract

1. Obtain a fresh login code through the real WeChat `wx.login` flow. Never invent a code or infer identity in the client.
2. Send `POST /v1/auth/wechat/session`, `Content-Type: application/json`, body `{"code":"the fresh login code","clientVersion":"wechat-platform-0.1.0","protocolVersion":1}`. The version fields are optional for isolated service tests; when present, protocolVersion must be `1`, and clientVersion must be 1-64 ASCII letters, digits, dots, underscores or hyphens. No other properties are accepted.
3. Success returns `{ok:true, sessionToken, playerId, expiresAt}`. Keep the short-lived opaque `sessionToken` in the current client memory as the existing platform adapter does. `playerId` is stable and `expiresAt` is an epoch-millisecond timestamp.
4. Inspect with `GET /v1/auth/session` and `Authorization: Bearer <sessionToken>`. The result contains `ok: true`, `playerId` and `expiresAt`.
5. Log out with `POST /v1/auth/logout`, the same Authorization header, JSON body `{}`. A successful response is `{"ok":true,"revoked":true}`. This revokes that session only.
6. On `401` discard the session and obtain a new code. On `403 WECHAT_RISK_REJECTED`, show that login was rejected and avoid an automatic retry loop. On `409 WECHAT_CODE_REUSED`, obtain a new code instead of replaying the previous code. On `429`, wait before trying again. `503` and `504` should show retryable unavailability, with no fake success state.

Errors use `{"error":{"code":"STABLE_CODE"}}`. The service never returns or logs raw OpenID, WeChat session key, login code, AppSecret, or identity key. Tokens are random 256-bit opaque values, default lifetime 30 minutes. Only SHA-256 token hashes are indexed in memory. Tokens are not accepted in URLs. Logout and expiration invalidate them; restarting the service invalidates all sessions. No refresh-token mechanism is provided yet.

## Deployment boundary and limits

Expose this isolated process behind HTTPS at a same-origin path or an appropriate WeChat request domain. Configure the registered game's backend domain settings in the WeChat console and test on a real device. The service adds no CORS headers and trusts no forwarded IP headers. Behind a proxy all users currently share the proxy's request bucket; a vetted trusted-proxy policy is required before multiuser deployment. Do not simply trust arbitrary `X-Forwarded-For`.

Defaults bound input to 1 KiB, request bodies to 5 seconds, upstream exchanges to 5 seconds, active handler requests to 32, concurrent WeChat exchanges to 8, sessions to 2,048, IP buckets to 2,048, and remembered code hashes to 4,096. Each source address gets up to 90 auth requests and 10 login attempts per minute. Replay entries last 10 minutes, including failed exchanges; a timeout consumes the submitted code locally, so the client must get a fresh one. Capacity exhaustion fails closed without evicting live sessions or replay guards. All storage is process-local; multiple instances need a shared durable session/replay/rate-limit store before scaling.

This service authenticates identity only. It does not add cloud saves, game entitlements, authoritative balances, payments, account recovery, nickname/avatar consent, or registration UI. A later save API must authenticate the token server-side and derive player ownership from the session, never a supplied player ID. Do not send this token to the unrelated presence WebSocket service or assume it already authenticates that service.

## Validation

Run `node --test service/wechat-auth.test.mjs tests/wechat-adapter.test.mjs`. Tests cover disabled/missing config, malformed and oversized payloads, fixed AppID, stable identity boundaries, independent tokens, revocation, expiry, code replay, concurrency, rate and capacity limits, upstream rejection/malformed responses, timeouts, and slow bodies. An integration test sends the adapter's actual JSON via HTTP to the real handler, parses its session response, verifies that token, and revokes it. Only the external WeChat response is injected for this path. These tests do not substitute for a real WeChat login using the registered game's credentials.
