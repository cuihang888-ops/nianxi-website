## Codex 的主责闭环

Codex 对外统一项目状态和协作入口，本轮专注微信平台与框架接入：

- 维护 GitHub 仓库、主分支和协作分支；确认每次改动基线、范围、测试和回滚点。
- 维护产品架构：客户端、平台适配、账号服务、世界服务、资产服务、经济服务和支付适配层之间的边界。
- 设计注册契约：平台登录结果只作为登录来源，由服务端验证并映射为安和里自己的 `accountId/playerId`；客户端不能自报账号归属、余额或资产所有者。
- 维护服务边界：未来权威安币、归属和资产操作由服务端确认；本轮保留免费规则与配置，不新增充值、订单或退款实现。
- 负责平台接入完整性：登录失败不生成假身份，存档失败不显示成功，前后台事件和网络状态如实传递给游戏；游戏内部场景与玩法闭环由 Muse 负责。
- 负责集成质量门槛：单元、服务、浏览器、微信接入、存档迁移和原自动罗盘校验；结合 Muse 的真机画面与玩法验收决定是否进入下一阶段。

真实充值开放前，Codex 还要核对主体资格、平台能力、商品目录、支付渠道、回调验签、退款、对账、客服和风控流程。客户端收到“支付成功”回调不能直接发放安币。

## Muse 的主责闭环

Muse 对内负责游戏画面、玩法、细节与游戏内部运行完整性，负责：

- 以稳定的 `regionId`、`settlementId`、`assetId` 和动画状态制作德宏原野、瑞丽总佛寺外围、江畔家园、动物、马匹和公共空间。
- 负责画面内的注册入口、昵称、安家、养动物、路线、照料、购买确认和错误反馈，使流程自然、可理解、可触控。
- 负责场景级运行：资源加载、点击命中、移动手感、镜头、碰撞代理、动画切换、LOD 和减少动态效果；发现服务或规则问题时提交复现记录，不在画面代码中绕过规则。
- 负责从进入游戏到游玩、收获、保存反馈及返回恢复的客户端闭环；对接 Codex 的平台接口，未接通的能力显示真实状态。
- 交付桌面与手机截图、素材来源与许可证、面数/绘制次数/纹理占用/帧时实测，以及缺失资源和低端设备问题列表。

Muse 可以实现注册和经济系统的**界面与客户端流程**，但注册结果、账号归属、权威余额、支付回调、退款状态和资产发放必须调用 Codex 约定的服务接口，不能由 React、Canvas 或本地存档直接决定。

## 稳定接口

第一阶段继续使用网页可运行的纯规则模块：

- `src/world-state.js`：区域、聚落、总佛寺、交通方式和路线计算。
- `src/farm-state.js`：安家、买马、养成、安币和旧存档迁移；旧余额与动物资产不因迁移改变。
- `wechat/project.config.json`、`wechat/game.json`：当前小游戏工程配置；`wechat/game.js` 启动运行宿主，`wechat/game-entry.js` 导出的 `createGame(context)` 当前指向平台诊断，Muse 在该入口接入游戏工厂。
- `wechat/platform/game-host.js`：管理一个 Canvas、帧循环、触控、窗口尺寸与前后台暂停恢复；接口见 `WECHAT_RUNTIME_CONTRACT.md`。诊断页不代表游戏场景已移植。
- `wechat/platform/wechat-adapter.js`：已提供登录、字符串存储与生命周期适配；`wechat/runtime-config.js` 的后端 URL 为空，当前未连接真实登录服务。
- `wechat/platform/save-repository.js`：已实现同步本地快照、版本冲突和写入失败反馈；`load()`、`save(state,{expectedRevision})` 只返回本机结果，`cloudSynced` 固定为 false，损坏或不兼容记录不自动覆盖。接口见 `WECHAT_SAVE_CONTRACT.md`。
- `scripts/build-wechat.mjs`：独立生成 `dist/wechat`，只包含小游戏代码、公开配置和允许的运行资源；不上传或发布。说明见 `WECHAT_BUILD.md`。
- `service/wechat-auth.mjs`：已实现独立微信登录交换、会话检查和注销；尚未部署，平台密钥及 HTTPS 域名待配置，不能把 mock 微信响应测试当作真实联调。
- `PlatformSession`：`startLogin()`, `getSession()`, `signOut()`；返回服务端验证后的玩家身份，不返回可由客户端修改的权威余额。
- 后续云端 `SaveRepository` 与迁移：仍需账号归属、服务端版本、冲突恢复与迁移设计；当前本地仓库未实现云存档或自动迁移。
- `WorldRenderer`：`loadRegion()`, `unloadRegion()`, `setPlayerState()`, `setAssetState()`；渲染回调不能改变钱包或家园归属。
- `InputAdapter`：只发送移动、选择、照料、购买确认和路线选择等语义指令，不把平台事件直接写进规则层。
- 后续服务命令：`POST /world/home`、`POST /assets/purchase`、`POST /payments/orders`、`POST /payments/webhook`。这些是设计契约，当前网页服务尚未提供全部端点。

## 禁止事项

- 不把 localStorage 的安币、土地或动物当作真实付费资产凭证；它只能作为当前网页原型存档。
- 不在客户端生成或修改 `playerId`、钱包余额、订单金额、支付结果、资产归属或退款状态。
- 不以假在线人数、假交易、假土地稀缺或“充值才能祈福/养活动物”制造压力。
- 不把瑞丽总佛寺当前功能原型宣传成官方复原、官方合作或精确测绘场景。
- 不把游戏路线分钟数当作现实德宏旅行时间，不把聚落当作现实土地权属。
- Muse 不整体覆盖 Codex 的规则、存档、服务和测试文件；Codex 不以规则通过替代画面和真机验收。
- 不把微信小游戏、账号云存档或充值说成已经完成，直到对应构建、真机和服务验收记录存在。

## 每轮交付与验收

每轮提交都要写明基线提交、修改文件、接口变化、测试命令和已知限制。至少完成：

1. 规则：非法 ID、重复购买、余额不足、重复通知和旧存档迁移均有测试。
2. 客户端：桌面/手机画面非空，真实点击命中，按钮和文字无溢出，保存失败有明确提示。
3. 场景：动物/马匹在碰撞范围内，动画状态可回收，区域切换释放资源，减少动态设置有效。
4. 服务：注册、断线重连、并发消费、幂等、服务重启和权限边界有可复现验证。
5. 微信目标：目标环境能启动最小场景并恢复测试存档后，才迁移更多区域和资产。

交付通过后由 Codex 合并到协作基线；未通过的部分保留在分支，不用截图或演示掩盖失败。

## 分支和 PR 流程

1. Codex 先在基线分支写清任务、接口和验收条件。
2. Muse 从最新基线创建自己的画面分支，提交只覆盖画面、资产和客户端交互范围；涉及规则参数先提变更说明。
3. Codex 在合并前检查冲突、读档兼容、服务边界、测试和安全扫描；必要时逐文件合并，不整体覆盖旧 ZIP。
4. 合并后重新跑网页测试、构建、罗盘校验和桌面/手机截图；微信适配分支另跑目标环境验证。
5. 只有用户明确要求发布时，Codex 才执行线上部署、微信提交或真实支付开关变更。

当前协作基线是 `codex/dehong-world-framework`；后续 Muse 游戏分支应从该基线或其最新合并提交创建。网页继续是共同回归入口，微信工程正在做平台接入，真实游戏迁移与真机验收尚未完成。
