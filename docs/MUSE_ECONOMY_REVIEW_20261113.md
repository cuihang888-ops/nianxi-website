# 安币经济模拟与阶段蓝图交接审查

日期：2026-11-13

本稿依据用户提供的 Muse 90 天经济模拟报告与第二份产品蓝图要点整理，压缩重复文字，保留参数、结果和决策边界。它不是两份原文的逐字副本。以下模拟结果均为 **Muse 提供**；当前没有收到对应模拟脚本、逐日账本或配置快照，Codex 尚未复跑，不能将结果表述为已经验证、经济已经跑通或参数已经采用。

## 当前决定

- 首发为年禧主体的微信小游戏免费体验版，不充值、不提现、不接商城订单和支付。
- 本轮把现有经济常量抽成可配置数值表，默认值保持不变，不改变免费版手感。每日补给仍为 `+120` 安币，不叠加登录 `+5` 或在线每小时 `+2`。
- 免费首发从第一天记录经济来源、消耗、余额和使用体验数据。累计签到、小确幸、回流礼等新增玩法保留在后续内容包，不作为本轮已实现功能。
- NPC 收购日限、动物盛产期、玩家交易、月卡和充值余额过渡均为后续设计，不在本轮启用。

## 模拟设定

Muse 报告采用 90 天确定性模拟，三类玩家如下。

| 玩家 | 假设行为 |
| --- | --- |
| A 免费轻度 | 每天登录，在线 1 小时，收 1 次产出，舒适度普通 |
| B 免费活跃 | 每天登录，在线 3 小时以上，收 2 次产出，舒适度至少 80、产量翻倍 |
| C 轻充值 | 同 A，每月充值 10 元，按 1,000 安币计算 |

购买策略：初始 1,200 安币买地和羊、兔、鸡；之后盈余先补动物再买地，保留 100 安币缓冲。报告以当前土地价、动物价和产出规则作为第一轮起点。

| 项目 | 报告使用的现值 |
| --- | --- |
| 土地 | 400 / 600 / 800 / 1,100 安币，每块容量 6 |
| 羊 | 领养 260；周期 30 秒；羊毛售价 32 |
| 兔 | 领养 180；周期 24 秒；兔毛售价 22 |
| 鸡 | 领养 140；周期 18 秒；鸡蛋售价 16 |
| 动物待收 | 单只最多 12；喂食后产出；舒适度至少 80 时产量乘 2 |
| 日常补给 | 当前代码为每日 120 安币，另送牧草和胡萝卜 |
| 狩猎 | 冷却 20 秒，成功山货售价 45；当前成败由客户端传入 |
| 蓝图保底收入 | 登录 5、在线每小时 2；这是待定新口径，不是当前已实现奖励 |

## 第一轮：直接沿用现数值

下表按 Muse 提供的结果保存，尚未复跑。

| 玩家 | 90 天余额 | 内容进度 | 报告保底收入（登录与在线） | 报告经营收入 |
| --- | ---: | --- | ---: | ---: |
| A 免费轻度 | 583,970 | 约第 2 周买满 | 630 | 589,680 |
| B 免费活跃 | 1,184,090 | 几天买满 | 990 | 1,189,440 |
| C 轻充值 | 585,970 | 同 A | 630 | 589,680 |

Muse 的解释：经营收入在总收入中占绝大部分，登录和在线奖励影响很小；报告计入的充值 2,000 安币约占总收入 0.3%，购买加速感很弱，现有内容很快耗尽。因此，当前单机快速循环的数值不宜直接作为充值经济参数。

该结论是设计风险提示，不是对真实玩家行为的验证。是否存在长期全服通胀还取决于玩家行为分布、喂养成本、内容消耗、产物实际售出量和发行规则。

## 第二轮：仅调整生产参数

| 参数 | 调整假设 |
| --- | --- |
| 羊 | 周期 12 小时，售价 6 |
| 兔 | 周期 8 小时，售价 4 |
| 鸡 | 周期 6 小时，售价 3 |
| 单只待收上限 | 4 |

报告结果：B 玩家第 90 天余额仍为 38,266；三类玩家均买满现有内容并积累闲置余额。A、C 的具体余额未在提供材料中列出，不补填。

Muse 的解释：动物一次领养后持续产出，单纯延长周期和降低售价只会推迟内容耗尽。这个判断需要把实际饲料消耗、种植成本、照料动作和购买顺序一起纳入复跑；现行代码并非不需要任何运行投入。

## 第三轮：参数与结构限制组合

在第二轮参数基础上，Muse 提出两个额外假设：

1. NPC 每位玩家每天只收购价值 80 安币的产物；超出部分由玩家市场承接，不由系统继续无限回购。
2. 动物盛产期 45 天，结束后成为陪伴动物，仍可摸、喂和留在院中，不死亡、不因缺席受到惩罚，但停止产出。

| 玩家 | 90 天余额 | 报告内容进度 |
| --- | ---: | --- |
| A 免费轻度 | 470 | 3 块地，仍在添置 |
| B 免费活跃 | 582 | 3 块地，仍在添置 |
| C 轻充值（月 10 元） | 110 | 第 90 天刚买满 |

Muse 将这一轮解释为“免费玩家持续有目标，轻付费加速但不购买资格”。目前这里只保存这个解释，不接受“已经跑通”作为验收结论；需要脚本、账本和多种玩家策略复跑后再决定是否采用。

## 复跑前必须统一的口径

| 问题 | 必须补齐的定义 |
| --- | --- |
| 每日补给与登录奖励 | 当前 `dailyGift` 是 120 安币，还提供 2 份牧草和 1 份胡萝卜。报告的 630 / 990 对应登录 5 与在线每小时 2，需说明 120 是否已被替换、饲料补给是否保留。两套安币奖励不能无意叠加。免费本轮仍保留 120。 |
| 90 天充值总额 | 报告说每月 10 元，第一轮只记入 2,000 安币。需列出具体到账日期、首日是否到账、月底还是月初、观察窗口是否含第 90 天；不能同时把“每月”当 30 天周期和日历月而不说明。 |
| 喂食与生产 | 实际 `feed` 每次消耗 1 份饲料并只延长 2 个生产周期；当剩余喂饱时间大于 2 个周期时拒绝继续喂食；等于阈值时仍可喂，最多形成约 4 个周期的储备。不得按全天无限持续产出计算。 |
| 待收上限与收取次数 | 当前上限为每只 12，满仓后时间仍向前推进，收取不会追回溢出产出。每天收 1 次和 2 次必须落实到时间轴，同时计算喂食、抚摸、种植、浇水、收获和出售动作。 |
| 舒适度 | 当前初始 55，喂食增加 8，抚摸增加 12、冷却 5 秒，80 起产量翻倍。不能在没有照料动作与耗时的情况下直接假设始终翻倍。 |
| 饲料和种植成本 | 牧草种子 12、产 3；胡萝卜种子 18、产 2，浇水后方可收获。需区分初始库存、每日补给、自产饲料、种子支出与实际消耗，避免把“无需真实充值”误当“没有运行成本”。 |
| 收购日限 | 80 安币日限需要玩家每日已售价值、统一重置时区、跨日边界、部分成交、幂等与并发校验。它不是只在常量表中增加一个数字即可生效。 |
| 动物退休 | 45 天需要出生/领养时间基准、状态字段、旧动物过渡、产出结算、容量占用与陪伴展示规则。退休动物若持续占满土地会阻断再次领养，需先解决，不可只改周期参数。 |
| 玩家市场 | 玩家交易不发行系统货币，但能否卖出依赖真实买家、需求、库存和价格。不得把所有超额产物都假设为必然成交，也不能用玩家市场代替总量和供需分析。 |
| 狩猎 | 当前客户端可传入成功结果，免费原型不能视为防作弊经济。联机或付费阶段必须由服务端验证动作/结果并明确次数、收购上限和山货发行规则。 |

复跑脚本应以固定时间和明确动作策略调用真实 `createFarm`、`advanceFarm`、`applyFarmAction`，逐笔记录成功或失败结果，不能只用“动物数量乘理论产出”代替实际规则。第二、三轮新规则尚不存在，必须把模拟分支、配置和新增规则实现一起提交，不能声称仅修改现有配置即可复现。

最低复跑产物：代码提交号、经济配置版本、完整动作日程、充值到账日程、逐日发行与回收账本、动物/土地/库存快照、购买完成日期，以及日志中每个失败动作的处理方式。还应覆盖错过登录、短时上线、长期离线、非最优购买、只养一种动物、不狩猎和过度狩猎等策略。

## 产品红线

蓝图强调治愈和低压力：不抽卡、不制造错过焦虑（FOMO）、不以断签或缺席惩罚玩家、不做竞争排名、不做概率付费、不限时逼氪、不设置体力付费门槛、不增加双币换算链。

基础祈愿、相聚与陪伴不收费；不出售好运、功德或宗教效果。动物不因缺席死亡。免费玩家能体验核心世界，未来付费优先提供明确内容和外观，不能把资格、尊严或情绪安全当商品。

月卡“每日必须领取，否则过期”的设计与上述低压力目标冲突。若第三期采用月卡，建议权益自动累积、允许补领，不用断领损失刺激上线；最终方案仍需单独确认。

## 免费首发数据要求

从免费版上线第一天开始，每位玩家每日记录必要的匿名或假名化统计，服务端接入后以服务端确认事件为准。当前本地原型统计只能辅助体验分析，不能充当防作弊账本。

| 数据 | 最少字段/分类 | 用途 |
| --- | --- | --- |
| 发行 `faucet` | 玩家假名 ID、日期、配置版本、动作/事件 ID、数量、原因；分类 `login / online / business / hunt / activity` | 看清钱从哪里来；未启用的来源为 0，不能为了统计新增奖励 |
| 回收 `sink` | 土地、动物、马匹、种子及后续装饰等分类；数量、原因、动作 ID | 判断消耗目标是否足够，避免重复扣款计数 |
| 余额快照 | 每日开始/结束余额、库存及内容进度摘要、存档版本 | 核对发行、回收与余额差额，识别存档覆盖和通胀迹象 |
| 登录与停留 | 会话 ID、开始/结束、前台有效停留、返回场景、退出/中断原因 | 区分真实游玩与后台挂起，计算留存和体验时长 |
| 运行质量 | 登录/存档失败、恢复、冲突、场景加载失败、异常退出 | 判断用户离开是否由技术问题造成 |

当前本地遥测把每日补给归入 `source=login`，并以 `action=dailyGift` 区分原因；这不表示另发了登录5安币。若第三期改口径必须升级统计版本，不能静默混用。狩猎成功只产生山货库存，不立即增加安币；出售山货时才记 `source=hunt`，不能成功和出售各记一次收入。普通产物售出归入 `business`。

事件需有稳定 ID、去重规则和统一日界。离线事件延后上传时保留发生时间和上报时间；跨设备、重试和刷新不能重复计数。不采集通讯录、手机号、精确位置或聊天内容来完成上述分析。尚未落地的签到、活动和付费指标明确标为未启用，不生成模拟运营数据。
