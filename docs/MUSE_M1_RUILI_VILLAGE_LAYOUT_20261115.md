# M1 · 瑞丽共享村落布局契约（2026-11-15，v2 放大版）

收件人：Codex。配套数据模块：`wechat/vendor/shared-village.cjs`（本文所有数值从该模块抄录，两边以模块为准；模块内有对应单元测试 `tests/shared-village.test.mjs`）。
基线：`codex/dehong-world-framework` @ `f92ab43`。本契约只定村落布局与坐标，不表示共享世界、云存档或多人已经接通。
v2 修订要点见 §10；旧值在该节有完整对照。

## 1. 坐标约定

- 右手系，Y 向上，地面为 X/Z；位置单位为游戏单位，不宣传为现实测绘米。
- `yaw` 为绕 +Y 的弧度，与现有 `dam-world.cjs` 的朝向约定一致：`yaw = atan2(dx, dz)`（yaw=0 朝 +Z/南，yaw=π 朝 −Z/北）。
- 北为 −Z，东为 +X（与现有瑞丽场景一致：姐勒金塔在坝内 (152,−118) 东北，瑞丽江在坝内 z≈170+ 南界）。
- **村落坐标系**：原点取现有瑞丽场景基址 site0「湖畔」中心。村落坐标轴与坝内坐标轴**平行、不旋转、不缩放**，只有平移：

  `村落坐标 = 坝内坐标 − (−64, 66)`，即 `x村 = x坝 + 64`，`z村 = z坝 − 66`（模块函数 `toVillageCoords` / `toDamCoords`）。

  原点依据：`wechat/vendor/ruili-scene.cjs` 的 spec `sites[0] = {x:-64, z:66}`（湖畔基址，引擎在此生成基址中心圆台与环绕地块）。选它作村心的理由：古道（见 §2）正穿过该基址北侧、系统集市在其东侧约 60 单位、弄莫湖在其西侧，村心、路、集市三者现成衔接，不需要另起一套坐标。
- 村落可走范围（村落坐标，**多边形**，模块 `BOUNDS_POLYGON`，判定函数 `pointInBounds`）：

  | 顶点 | 村落坐标 | 取界依据 |
  | --- | --- | --- |
  | 北界西段起 | (−52, −90) | 北界为坝内 z=−24 一线，北侧丘陵碰撞圈均在界外 |
  | 北界东端 | (48, −90) | 同上 |
  | 东界北段 | (48, −28) | 集市空地圆盘（村落 (64,−60) r15）与大厅一带留在界外东侧 |
  | 河岸凸出段北端 | (62, −28) | 集市圆盘南沿（z=−45）以南 17，步道沿河岸西侧南伸 |
  | 东南角 | (62, 88) | 南宛河渲染河道西沿在此 z 约 64（距界 1.3 以上为水面外余量，spec 水圆更远） |
  | 南界西端 | (−100, 88) | 瑞丽江水面北沿约 z=94，南界留 6 余量 |
  | 湖岸凸出段 | (−100, 18) | 弄莫湖渲染南沿 17.5 以南，湖区西南的湖岸草地划入 |
  | 湖东凹口 | (−52, 18) | 弄莫湖 spec 东沿 −55、渲染东沿 −53.5，均在界外 |

  多边形面积 **22784**（鞋带公式实测，测试断言），是 v1 矩形范围（90×120 = 10800）的约 **2.11 倍**。形状说明：主体是沿古道东西向拉长的村域（包围盒 x∈[−100, 62]、z∈[−90, 88]），西侧为湖东让出凹口、南侧住区展开到江岸草地、东南一角沿南宛河西岸收窄——全部凹凸都是顺应现有水面与集市/大厅锚点，不是随手画的。现有场景的全部 spec 水面圆心与丘陵碰撞圈圆心均在多边形之外（测试逐项断言），宿主锚点（集市、大厅、水晶）一个未动：集市、水晶仍在界外，大厅亭 (37,−74) 随北界扩大落在村落北缘范围内，作为保留点不划地块（见 §4）。

## 2. 村路

村内主路沿用现有古道的南段折线（`ruili-scene.cjs` decorate 的 `roadPts`），不新画一条对不上的路——原始社会的村子只有这一条土路：

| 点 | 村落坐标 | 坝内坐标 | 说明 |
| --- | --- | --- | --- |
| 西口/路口 | (−46, −40) | (−110, 26) | 古道既有折点；向西接古道去弄岛方向，村外上一折点为村落坐标 (−126, −22)（坝内 (−190, 44)） |
| 中点 | (24, −54) | (−40, 12) | 古道既有折点 |
| 东门 | (44, −57) | (−20, 9) | 古道段 (−40,12)→(0,6) 在村界处的中点（t=0.5）；出东门即集市 |

- 路宽：古道视觉圆盘半径 4.4，契约取道路走廊半宽 **5**（模块 `ROAD_HALF_WIDTH`）。
- **地块不得压路判定规则**：地块多边形任一边与道路中心线折线的最短距离（边对边）必须 **≥ 8**（= 半宽 5 + 余量 3，模块 `ROAD_CLEARANCE`，判定函数 `isClearOfRoad` / `distancePolygonToRoad`）。后续新增地块、装饰占地一律按此判定，不以“看起来没压上”为准。
- 路口只有两处：西口（接古道西段）与东门（接集市/寺院通路），村内不设其他出入口；地块户门统一朝路开（见 §3）。村内排布的「巷/径」只是地块之间的土空地，不是新画的路。

## 5. 寺院通路

总佛寺（`templeId = ruili-temple`）**不在现有瑞丽坝场景范围内**（坝内无总佛寺建筑；东北山丘上的是姐勒金塔，不同对象，见 §6）。本村只交“通路出口 + 方向 + 里程碑锚点”，不编造寺院内部坐标：

- 通路折线（村落坐标）：东门 (44, −57) → 集市 (64, −60) → 里程碑 (134, −50)（坝内 (70, 16)，古道东段既有折点）。出里程碑后出坝往总佛寺方向，寺院本体是后续场景。
- 方向：自东门向集市的方位 yaw = atan2(20, −3) ≈ **1.720 rad**（东偏北）。
- 锚点命名（先行约定，**待 Codex 冻结**）：下马锚点 `ruili-temple-gate-dismount`、入院锚点 `ruili-temple-gate-entry`、红结锚点前缀 `ruili-temple-knot-`（后接 `tree-01` / `rack-01` 等）。里程碑 id 建议 `ruili-river-0001-temple-milestone`。下马/入院/红结锚点的具体坐标由寺院场景交付时在寺院坐标系内给出，本村不预设。

## 6. 金塔祈福点（姐勒金塔）

姐勒金塔是现有瑞丽场景里本来就有的大地标（v1 契约只管村落与寺院通路、没把它纳入锚点体系，俯视图上也没画——用户 2026-11-15 指出「大金塔怎么消失了」，v2 正式补入）。用户要求：金塔是**可进入的祈福场所**，玩家能到塔里做祈福等一系列动作。

- **坐标来源（现有场景实有数据，不新编）**：`ruili-scene.cjs` decorate 中，金塔建在坝内 **(152, −118)** 的山丘上——丘体圆锥 r30、h15，塔身为多层金顶，碰撞圈 `{x:152, z:−118, r:16}`。换算村落坐标：塔中心 **(216, −184)**（模块 `PAGODA`）。它在村落东北、坝内可达范围内（坝界椭圆 rx250/rz205 内），动线是沿古道东行出村、过集市、再北上塔山；它不在村落可走多边形内，本契约作**坝内地标锚点**管理，小地图上作方向地标（见 §8）。
- **锚点（本契约只定到这一层）**：

  | 锚点 | 值 | 说明 |
  | --- | --- | --- |
  | 塔中心 | 村落 (216, −184) | 同上，含 `hillRadius 30`、`colliderRadius 16`（均抄现有场景） |
  | 塔门入口 `entry` | 村落 (205, −175)，判定半径 4 | 相对塔中心局部偏移 (−11, 9)：在塔基朝村落/古道一侧（西南侧），距中心约 14.2，在碰撞圈内缘——走到这里触发「入塔」 |

## 7. 村落扩展规则

- 目录现状：本村共 **8 块地块位**（§3 表），样板 2 块 + 预留 6 块在本契约里全部定死坐标。**启用顺序**（模块 `EXPANSION.enableOrder`）：先第 0 排样板两户 → 第 1 排西→东（C、D、E）→ 第 2 排西→东（F、G、H），即先近路、后向南，同排西先东后。
- 编号：plotId 后缀按启用顺序 a→h 递增（服务端目录为准）；既有地块坐标一经分配永不移动、不重排。
- 保留区：主路走廊（§2 判定）、村心空地、出生歇脚处、井/榕树公共点（§4）、大厅亭周边，任何排布不得侵入；新排布落地前先跑 `isClearOfRoad`、保留区相交与水面/丘陵距离检查（本轮 8 块的检查结果在测试里）。
- 本目录 8 块排满后扩新村：本村坐标、地块与公共点全部不变；新村是同地区另一个 `villageId`，自带自己的原点与目录（交接文档：村落满了由服务端扩展同地区新村落）。村内不再向东/北见缝插针加地块——东是河道与集市、北隔路是大厅与出村方向，硬加只会压水压路。

## 8. 小地图投影方法

- 投影（模块 `worldToMap` / `mapToWorld`，互为逆变换，测试覆盖）：以村心为投影中心，比例 **2 地图单位 / 游戏单位**：

  `map.x = (x − 0) × 2`，`map.y = (z − 0) × 2`

  map.x 东为正；map.y 向下为正，即 +Z（南）在下、−Z（北）在上，**指北向上**，与俯视布局图一致。
- 自身朝向箭头：玩家 yaw 按 §1 约定（yaw = atan2(dx, dz)）；地图上箭头角度 θ 满足：朝北（yaw=π）时箭头指向上。渲染时 θ = yaw + π（把“朝向向量 (sin yaw, cos yaw)”映到地图向量 (sin yaw, −cos yaw) 后取屏幕角），实现时以朝向向量投影为准，不另设角度表。
- 地标点投影：家（自家地块原点）、集市 (64, −60)、大厅 (37, −74)、水晶 (70.5, −55.5)、**姐勒金塔 (216, −184)** 均用同一 `worldToMap` 投影；寺院不在本图范围内，只画**东门出口 + 朝集市/里程碑方向的指向标**，不画假寺院点；金塔是坝内实有地标，可以画点，但超出村落地图视窗时按既有小地图做法显示方向/远近，不编造距离数字。区域出口同理只标西口与东门。
- 地图定位只读：选目的地、取消路线均不触发传送（交接文档红线）。

## 12. 施工记录（2026-11-15，M1 场景施工第一块）

本节记录本契约在微信小游戏瑞丽场景里的第一次落地。数值仍以 `shared-village.cjs` 为唯一来源，本节不另立坐标。

**实际建了什么**
- 共享村落落位（`wechat/vendor/ruili-scene.cjs` + 通用引擎 `dam-world.cjs` 新增 `spec.siteLayouts` / `spec.decoratePlot` 通用钩子）：site0「湖畔」的 8 块地按契约坐标排布（30×32 垫面、启用顺序 = idx 0–7），村心空地南北贯通（土面长条）、排间土巷、井台 + 榕树公共点（井边空地 disc 按契约保留半径 8 画）都已建进场景；出生圆台仍是引擎在基址中心生成的石台，未动。
- 地块交互锚点（给下一块注册闭环预留）：每块地的 plotId 与契约 `ALL_PLOTS` 的 id 一一对应，经引擎 `getPlots()` 与 `nearestInteractable()` 透出（`{id, reserved, site, idx}`）；认领/建家逻辑下一块直接按 plotId 对接，不需要再猜位置。
- 样板地 A/B 的格局示意：按契约 layout 锚点只画线——地基线（house 位）、4 条田畦线（beds 位）、院落圈（animalZone 位）——只有线框、没有任何物件冒充已入住；初始状态 8 块地全部 `claimed=false`。认领发生时引擎自动撤下该块的示意线与木牌，换上认领自带的地基与木牌（`markClaimedVisual` 统一处理）。
- 预留地 C–H：垫面 + 木牌 + 门前横木栏（地已划好、门未开），交互上不可新认领（动作钮显示「预留地 · 尚未开放」，点了只给一句说明，不扣币不写存档）。
- 木牌是素板没有文字：本运行时没有可移植的画布贴图通道（微信端需平台画布、节点测试端无画布），沿用现有认领木牌的素板视觉语言；「预留」的文案诚实由动作钮与横木栏承担，plotId 文案在交互层。

**地块共存方案（选了哪种、为什么）**
- 选「垫面优先、认领落垫面」：site0 的 plotList 直接由契约 8 块地构成（同 site/idx 键位），本地认领/草棚/田/动物流程原样跑，视觉落在契约垫面上；原引擎在 site0 的 8 块环形小地（7.6×7.6、半径 11.5 环）整体撤下，不再与契约垫面叠出两套地块。site1「塔下」与其它四坝保持原环形地块不动。
- 存量存档：家园状态按 (dam, site, idx) 存，键位不变、数据不丢；老存档在瑞丽 site0 的家，视觉位置会从旧环位移到同 idx 的契约地块位（idx 与启用顺序一致：0=A、1=B……7=H），`restoreVisual` 照常恢复草棚/田/动物。预留标记只拦「新认领」，存量恢复不受拦（老存档若落在 C–H，照常恢复为自家地）。
- 已知小限：自选地块（custom plot）的占位判定仍是引擎原有的中心距规则，在村落排间土巷一带理论上可能与契约垫面边角轻微叠面（垫面是平的，视觉上是自选地基压在预留垫面边上）；村域内自选点还要过离基址 ≥16、离水/碰撞等原有校验，实际触发面很小，本块未为此新造判定系统，留待闭环块统一处理。

**金塔入塔祈福（实现方式与取舍）**
- 落地形态：塔山西南山脚的「塔基礼拜庭」——石圈土面庭院、塔门（两柱一梁 + 金顶珠，朝村落一侧）、靠山脚的佛龛（石壁 + 金身 + 供碗 + 灯柱）、龛前蒲团、引路踏石。走到庭前（入口锚点判定，见下）出现「入塔祈福」→ 位置转移到龛前礼拜位并面塔 → 合掌（1.6 秒）→ 礼拜（1.8 秒）→ 静坐祈福（复用静心 5 秒呼吸时长与静坐姿势）→ 绕塔一周（山脚地面光点环亮起，绕满一圈判定完成）→ 出塔。全程不发币、不加产量、不写存档、不挂红结（红结仍只在总佛寺）；骑马时先走现有「下马」流程，下了马才出入塔动作。流程由 `home-controller` 的祈福状态机驱动，姿势/光环是引擎新增的通用开关（`setPrayerPose` / `setGuideRingVisible`）。
- 与契约 §6 的两处落地偏差（如实记录）：① 祈福位未落在契约的塔基台面局部点 (0, 3.5)——现有塔体是实心丘体 + 塔身，没有登塔路径与室内结构，硬把人放上台面就是穿模假室内；本块把礼拜位落在山脚礼拜庭的龛前（入口锚点同侧、同一朝向），锚点体系不变，待后续做登塔/室内结构时再启用台面祈福位。② 绕塔半径由契约 9（台面环行）改为 20（山脚环行）：9 在现有几何里落在丘体内部，20 是山脚可实际走通的最小整圈（已核对不撞其它丘陵碰撞圈与水面）。③ 入口触发半径由契约判定 4 放宽到 8.5：玩家被塔山碰撞圈（r16）与佛龛碰撞挡住，站在庭心正中距锚点约 8.3，4 或 6 都触发不到（施工中实测发现并已修正、截图复验触发成功）。
- 图鉴：金塔地标点（`LANDMARK_SPOTS.ruili` 的 rl-pagoda）本就存在，走到塔山即收录；手记文案已改为与可入塔祈福一致。
